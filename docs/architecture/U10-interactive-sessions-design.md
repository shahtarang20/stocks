# U10 Interactive sessions (design note)

Status: code written, NOT executed or tested. Relay provider is an OWNER DECISION (see section 6).

## 1. Goal
Terminal (and later Jupyter / desktop) access to a rented GPU from a browser, with the host behind home NAT and no open port, and a relay that cannot read the traffic. Checkpoints (ADR-0006 WP-U10): U10.1 works behind NAT, U10.2 relay sees only ciphertext, U10.3 idle stops the session and the billing.

## 2. Topology
```
browser --wss--> API relay <--wss-- host agent --> docker exec (pty | loopback TCP bridge) --> session container
```
Both ends dial OUT to `/v1/sessions/{id}/relay/{browser|host}`. The container has `--network none` (or the B5 internal network plus egress proxy only when `network_policy.egress` is declared), publishes no port, and is the executor's hardened argv (read-only rootfs, no caps, no-new-privileges, non-root, pids/memory limits, GPU and isolation flags). Private tiers are refused by the API and the agent (U18 adds them).

## 3. End-to-end handshake (relay holds no key)
Browser creates an ephemeral X25519 key `eb` before the session and sends `eb_pub` in `POST /v1/sessions`. The agent creates a per-session static X25519 key `sa` and publishes `sa_pub` in the claim. On every (re)connect:
1. B -> A text `{"type":"hello","epk":eb_pub}`.
2. A makes a fresh ephemeral `ea`, answers `{"type":"hello_ack","epk":ea_pub}`.
3. `ikm = DH(sa,eb) || DH(ea,eb)`; `keys = HKDF-SHA256(ikm, salt=sha256(session_id), info="ccsess-v1"||eb_pub||sa_pub||ea_pub, 64)`; `k_b2a = keys[:32]`, `k_a2b = keys[32:]`.
4. Data = WebSocket binary frames, ChaCha20-Poly1305, nonce = 4 zero bytes || 64-bit counter (implicit, per direction), AAD = session_id || direction byte (0 B->A, 1 A->B). A drop, replay or reorder fails authentication and the socket is dropped.
5. Plaintext = type byte + payload: 0 data, 1 resize `{"rows","cols"}`, 2 close, 3 ready (first A->B frame after the handshake).
Forward secrecy comes from `ea` (reconnects re-key). The relay sees only the two public keys and ciphertext lengths and timing.

Known limit: public keys travel through the control plane (`host_pubkey` in the session record). A malicious or compromised API could substitute keys and mount a man in the middle. A pure relay on its own cannot be trusted for key distribution. Mitigations to decide later: sign `sa_pub` with the machine attestation key (U18 / ADR-0005 receipts) and let the browser verify, or show a fingerprint the customer compares through a second channel. Until then the claim is "a passive or honest-but-curious relay cannot read traffic", not "a hostile control plane cannot".

## 4. Lifecycle and tokens
States: `pending` (funded, waiting for a host) -> `starting` (claimed, not billed) -> `active` (host reported running, billed) -> `stopped | failed`.
- Create validates tier (private refused), exactly one of `kit_ref` / pinned `image_digest` (custom images off unless `SESSIONS_ALLOW_BYOC_IMAGE`, pending the U8 scan), limits, B5 network policy, and holds the worst case (`max_price_per_gpu_hour x gpus x max_duration` plus the platform fee) under `sess-hold:<id>`.
- Host claims with the machine HMAC (`POST /v1/agent/sessions/claim`), only a session whose max price covers the machine's asking price; the claim is an atomic conditional UPDATE. The response carries a 60 s single-use host token. `/token` mints a new one for reconnects.
- Browser calls `POST /v1/sessions/{id}/connect-token` (owner only): 60 s, single use.
- Tokens are stored as SHA-256 hashes, consumed by an atomic `UPDATE ... WHERE used_at IS NULL AND expires_at > now`, and wiped on stop.
- Host heartbeat every 20 s (`/heartbeat`) carries nothing secret; the response says `stop`. Missing heartbeats for 90 s -> `host_lost`, billed only to the last heartbeat.
- Stop: user `stop`, idle, max duration, host lost, unclaimed (10 min), start timeout (5 min), host `ended`. Every path calls `stop_session`, which is idempotent.

## 5. Billing (no change to ledger, pricing, billing)
Uses `ledger.post_transaction`, `billing._meter_actual_cost`, `pricing.get_active_fee_rate`, `spend_limits.check_spend_allowed`. Billed seconds = `stopped_at - started_at` (capped at max duration, floored at `BILLING_MIN_BILLABLE_SECONDS` once it ran); never for pending/starting. Capture splits provider earnings and platform fee like `settle_job` (`sess-capture:<id>`), the rest is released (`sess-release:<id>`). A session that never became active is fully released.
Idle = no BINARY relay frame in either direction for `idle_timeout_seconds` (60 s .. 24 h). Text frames (handshake, `ping`) and heartbeats do not count, so keepalives cannot hide idleness. Output from a long-running program counts as activity; this is a documented trade-off, because the relay cannot see content.
Enforcement points: relay socket watchdog (every 5 s), host heartbeat, `GET /v1/sessions/{id}`, and `sessions.reap(db, relay)`, which `app/worker.py` calls on every sweep (its own try/except, so a reaper failure does not stop lease recovery).

## 6. Relay provider (owner decision)
`services/session_relay.py` defines `RelayBackend` (attach, detach, forward, close_session, plus the process-local `peer_connected` / `last_activity` and their shared-state async forms `peer_connected_async` / `last_activity_async`). Shipped: `MemoryRelayBackend` (ONE API worker only) and `RedisRelayBackend` (several workers, selected with `SESSIONS_RELAY_BACKEND=redis`, uses `REDIS_URL`). The Redis backend uses pub/sub channels `relay:{session}:{side}` with a one-byte payload prefix (`B` binary, `T` text, `C` close, `R` replaced-by-token), presence keys `relay:peer:{session}:{side}` (30 s TTL, refreshed every 10 s) and an activity key `relay:act:{session}` (written at most once per second, binary frames only). Nothing is buffered: a frame for a side nobody subscribes to is dropped. Frames stay ciphertext in Redis. Its redis-py calls are unchecked against the current docs (marked TODO(verify-docs) in the code) and it has only been exercised against an in-memory fake. An external relay (for example a TURN/WebSocket gateway) can replace both with `set_relay()`; the agent only needs a different `relay_url`. Because payload is end-to-end encrypted, the provider needs no trust with content, only availability. With the default memory backend, run the API with a single worker (or sticky routing per session).

## 7. Modes
`pty`: `docker exec -it <container> <kit command or /bin/bash>` on a host pty. `tcp`: `docker exec -i <container> nc 127.0.0.1 <port>` (the container has no network, so the host cannot dial it); one stream per channel. Kits declare `manifest.session` (section 10). Jupyter or a desktop in a browser uses the HTTP-over-channel proxy (section 9). In `pty` mode the container must keep running on its own (image CMD) and the agent `exec`s the kit command into it; in `tcp` mode the kit command IS the container's main process.

## 9. HTTP proxy page (written, never run)
Goal: the browser reaches an HTTP app on the session container's loopback port (tcp mode) with no open port anywhere. Nothing about the relay or the handshake changes: HTTP rides inside the existing end-to-end encrypted channel as a new plaintext type, `4 = http`. The relay still sees only ciphertext lengths and timing. Older agents ignore type 4.

Framing (plaintext type 4 payload = `kind u8 | request id u32 BE | data`; ids are chosen by the browser; one id per request or tunnel):
- `0 REQ_HEAD` json `{method, path, headers:[[name,value]]}`; `1 REQ_BODY` raw chunk (<= 64 KiB); `2 REQ_END` (the agent sends the request upstream now).
- `3 RES_HEAD` json `{status, headers:[[name,value]]}`; `4 RES_BODY` decoded chunk; `5 RES_END`.
- `6 ERR` json `{code}` (ends the request); `10 CANCEL` (browser gave up).
- `7 WS_OPEN` json `{path, headers}` (WebSocket upgrade); the agent does the RFC 6455 handshake itself (own key, Origin rewritten), answers `RES_HEAD` (status 101 on success, only `sec-websocket-protocol` kept), then both sides exchange `8 WS_DATA` = raw RFC 6455 frames as an opaque binary tunnel (the browser codec masks and parses them); `9 WS_CLOSE` ends the tunnel.

Agent (`computecoin_agent/session_http.py`, wired in `session_agent.py`, tcp mode only): per request one `docker exec -i <container> nc 127.0.0.1 <tcp_port>` stream (container is `--network none`, nothing is published; the existing bridge). Method allowlist (GET HEAD POST PUT PATCH DELETE OPTIONS); path must be printable ASCII starting with `/`, <= 4096; request header NAME allowlist (accept, accept-language, cache-control, content-type, cookie, if-*, pragma, range, x-xsrftoken, x-csrftoken, x-requested-with, sec-websocket-protocol), no CR/LF/NUL in values; Host is `127.0.0.1:<port>`, `Accept-Encoding: identity`, `Connection: close`, Origin set to the loopback origin for unsafe methods and WebSockets; Authorization is never forwarded. Response: hop-by-hop headers and Content-Length removed (body is re-framed), Set-Cookie loses its `Domain=`, `Location` to the loopback address becomes path-relative, a non-identity Content-Encoding is refused. Caps: head 64 KiB, request body 8 MiB, response body 64 MiB, 16 concurrent requests, 8 WebSocket tunnels, 60 s to the response head. The container gets `COMPUTECOIN_SESSION_BASE_PATH=/dashboard/sessions/<id>/proxy/` so an app that supports a URL prefix (Jupyter `--ServerApp.base_url`) can be told where it is served.

Browser (`apps/web/src/app/dashboard/sessions/[sessionId]/web/page.tsx`, `lib/session-http.ts`, `public/session-sw.js`): the page owns the channel, registers the service worker (scope `/dashboard/sessions/`) and shows an iframe at `/dashboard/sessions/<id>/proxy/`. The worker is stateless: for each request under that prefix (and each root-absolute subresource request from a page living under it) it finds the owning `/web` page, sends it the request and a fresh `MessageChannel` port, and streams the page's `head`/`body`/`end`/`err` replies back as a `Response`. HTML responses are buffered (<= 8 MiB) and get a script that replaces `WebSocket` for same-origin URLs with a shim calling the parent page, which opens a `WS_OPEN` tunnel. The page keeps a small in-memory cookie jar (a synthesized Response cannot set cookies); `Set-Cookie` is absorbed there and replayed as `Cookie` on later requests.

SECURITY (owner decision, must be made before use): the iframe content is supplied by the HOST, which the customer does not trust. The service worker design forces it to be same-origin with the page that holds the channel, so that origin must NOT be the dashboard origin (the content could call the API as the user). The page therefore refuses to run unless `NEXT_PUBLIC_SESSION_PROXY_ORIGIN` names a separate origin serving the same web app (ideally another registrable domain, no shared cookies). The dashboard only launches it: it mints a connect token and opens `<origin>/dashboard/sessions/<id>/web#k=<client private key>&t=<token>&h=<host pubkey>`; the fragment is never sent to a server and is erased from history on load. `NEXT_PUBLIC_SESSION_PROXY_ALLOW_SAME_ORIGIN=1` exists for local development only. The known key-substitution limit of section 3 applies doubly here, because a hostile control plane could hand the browser its own host key.

Limits: no Set-Cookie attributes (Path, expiry kept only as max-age/expires deletion), cookies are per proxy page; no reconnect inside a page (the token is single use; reopen from the dashboard); in-page top-level navigations to root-absolute URLs that the app builds without the base path leave the service worker scope (use the base path env var); no HTTP/2, no server-sent-event specific handling beyond streaming bodies, no streaming request bodies, no `Authorization`; workers, `fetch` from cross-origin pages and WebSockets to other hosts are not proxied; HTML larger than 8 MiB is refused; service workers need a secure context (HTTPS); a browser that kills the worker mid-stream loses that response only. Every request is a new `docker exec` (tens of ms): fine for notebooks, slow for asset-heavy desktops.

## 10. Kit session block
Optional signed manifest key (validated strictly in `services/kits.py::validate_session_block`, unknown keys refused):
`"session": {"mode": "terminal"|"tcp", "tcp_port": 1024-65535 (tcp only, required), "command": [str, ...] (1 to 32 args, each <= 1024 chars, first non-empty), "idle_timeout_seconds": 60-86400}`.
`POST /v1/sessions` with `kit_ref` builds the session from it (`services/sessions.py::create_session`): the image digest comes from the Kit row (a request `image_digest` is refused), mode `terminal` -> `pty`, mode and port override the request, the effective idle timeout is the smaller of the request and the kit value, the block is re-validated (fail closed), private tiers stay refused, and there is NO network unless the Kit declares `egress`: the policy is the Kit's list, a request may only narrow it (`egress_not_declared_by_kit` otherwise). The agent runs the same hardened argv as every session; for `tcp` it appends `--entrypoint command[0] <image> command[1:]` (the kit command is the long-running server) and exports `COMPUTECOIN_SESSION_BASE_PATH`; for `terminal` the command is `exec`'d (default `/bin/bash`) and the image must keep the container alive. A Kit that carries a session block must declare manifest `mode: "session"` and a `mode: "session"` Kit must carry the block (`session_block_requires_mode_session` / `session_block_required_for_mode_session`, `services/kits.py`); `POST /v1/sessions` accepts only such Kits (`kit_mode_not_session`, 422).
