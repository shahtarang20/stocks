# Supervisor to runner control channel (W4) and the Windows supervisor (W2)

_Status: code written, **never run** (no Windows machine, no test run in this work). Plan:
[cross-platform-windows-linux-master-plan.md](../operations/cross-platform-windows-linux-master-plan.md) section 3.3, work packages W2 and W4.
Code: `provider-agent/computecoin_agent/control_channel.py`, `provider-agent/computecoin_agent/windows/`._

## 1. Roles

| Process | Where | Role on the channel |
|---|---|---|
| Runner (`computecoin-agent work --control-socket HOST:PORT`) | Linux: any host; Windows: inside the managed WSL2 distro | **Server**. Obeys commands, reports job events. |
| Supervisor (Windows Service) | Windows | **Client**. Owns heartbeat, thermal guard, availability, runner lifecycle. |

Without `--control-socket` the runner is unchanged (Linux behaviour does not change). With it, **nothing is claimed until
the supervisor sends `start`** (fail closed).

## 2. Transport and authentication

* TCP to a **literal loopback address** (`127.0.0.0/8`, `::1`). `0.0.0.0`, `::`, multicast, public addresses and host
  names are refused at construction. A private or link-local literal (the distro's address) is accepted only with
  `--control-allow-private` / `allow_private=True`. There is no LAN listener.
* The server also refuses a peer that is not loopback (or private, when allowed).
* One **per-install token**: 256 random bits, generated by the supervisor, kept in DPAPI (secret name `control_token`),
  written into the distro as a mode-600 file owned by the runner user, read by the runner with `--control-token-file`
  (or `COMPUTECOIN_CONTROL_TOKEN`). **Never on a command line.** On POSIX a token file readable by group or others is refused.
* Handshake (the token never crosses the wire):

```
server -> client : {"v":1,"type":"hello","nonce":<16 random bytes hex>}
client -> server : {"v":1,"type":"auth","cnonce":<16 random bytes hex>,
                    "mac":HMAC-SHA256(token, "cc-ctl-v1|client|" || nonce || cnonce)}
server -> client : {"v":1,"type":"auth_ok","mac":HMAC-SHA256(token, "cc-ctl-v1|server|" || nonce || cnonce)}
session key      = HMAC-SHA256(token, "cc-ctl-v1|session|" || nonce || cnonce)
```

  MACs are compared with `hmac.compare_digest`. The client verifies the server's MAC too (mutual). A wrong token closes the
  connection with no detail.
* After the handshake every frame is `length(4, big endian) || json || mac(32)`. The MAC covers a direction byte (`C`/`S`),
  a per-direction 64-bit counter and the JSON, so frames cannot be replayed, reordered, reflected or injected by something
  that only sees the stream. The envelope `seq` must equal the counter.

## 3. Caps

| Cap | Value | On breach |
|---|---|---|
| Handshake frame | 512 bytes | connection closed |
| Message frame | 64 KiB, checked **before** the body is read | connection closed |
| Mid-frame stall | 5 s | connection closed |
| Messages per connection | 50 per second, burst 100 | connection closed |
| Connection attempts | 20 per 10 s | refused |
| Auth failures | 5 per 60 s | 30 s lockout (everything refused) |
| Sessions | one at a time; a newly authenticated session replaces the old one | old one closed |

## 4. Messages (version 1)

Envelope: `{"v":1,"seq":<n>,"type":"...","data":{...}}`. Unknown types, unknown fields, wrong types and out-of-range numbers are
refused. A type is only valid in its own direction.

| Direction | `type` | `data` |
|---|---|---|
| supervisor to runner | `start` | optional `max_concurrent_jobs` (0..64), `availability` |
| | `drain` | optional `reason` |
| | `stop` | optional `reason`, `grace_seconds` (0..3600) |
| | `set_limits` | at least one of `max_concurrent_jobs`, `gpu_temp_cap_c`, `gpu_temp_resume_c`, `gpu_temp_hard_stop_c` (resume < cap < hard stop), `gpu_power_limit_w` |
| | `set_availability` | `availability` in `online, throttled, yielding, maintenance, draining`; optional `gpu_temp_c` (native reading) |
| runner to supervisor | `ready` | `agent_version`, `protocol`, `state` (`waiting` or `started`); sent right after authentication |
| | `job_started` | `job_id`, `active_jobs` |
| | `job_finished` | `job_id`, `status`, `active_jobs`, `draining` |
| | `error` | `code`, optional `message`, `ref_seq` |
| | `usage` | snapshot: `active_jobs`, `draining`, `availability`, `started`, `stopped`, optional `jobs_completed`, `jobs_failed`, `uptime_s`, `max_concurrent` |

The runner answers every command with a `usage` snapshot, and an invalid command with an `error` first (the command changes nothing:
limits are applied atomically). The supervisor learns that a drain has finished from a `usage`/`job_finished` showing
`draining: true` and `active_jobs: 0`.

## 5. Runner semantics

A claim is made only when **all** hold: `start` received; not draining; not stopped; availability is `online`; active jobs below
`max_concurrent_jobs` (default 1); and the supervisor has not been gone longer than 120 s (a running job is never killed because the
supervisor vanished).

* **drain**: the current job finishes, nothing new is claimed. Sticky until a new `start`.
* **stop**: nothing new is claimed and the claim loop ends after the current job. The runner has **no safe cancel path** for an
  in-flight job, so `stop` does not abort it: the supervisor enforces its own timeout and terminates the runner process
  (the server-side lease then expires and the job is re-queued). This is stated honestly rather than faked.
* **set_availability** is reversible; `gpu_temp_c` feeds the runner's `ThermalGuard`, so the existing hard stop in the Docker
  executor works from the Windows-native reading. A missing or stale (over 30 s) reading never blocks (existing ThermalGuard rule).
* **set_limits** thermal values are validated together; the runner refuses them when it has no thermal guard.

## 6. Supervisor behaviour (W2)

* Heartbeat: reuses `heartbeat.send_contract_heartbeat`. The API accepts `online | maintenance | offline | throttled`, and
  `maintenance` is a sticky owner hold, so every non-online state is sent as `throttled` and the real state travels in the additive
  health field `availability_detail` (same mapping as `windows/governance/policy.py`).
* `online` is reported only when the runner is connected, started and nothing blocks claims. Precedence: draining, maintenance,
  yielding, throttled, online.
* Telemetry: `telemetry.sample_gpu_metrics` (NVML). Its **simulated fallback sample is dropped** so a fake temperature never feeds the
  thermal guard or the heartbeat.
* Runner lifecycle: `wsl.exe --distribution <d> --user <u> --exec <program>` (argv list, no shell, via `windows/runtime/wsl.py`);
  restart with backoff (2, 5, 15, 30, 60 s); more than 5 restarts in 300 s gives up and reports `maintenance`.
* Stop (service stop, default 25 s, the Windows control handler must return within 30 s): report `throttled/stopping`, `drain`, wait up to
  20 s (never over half the timeout), `stop`, wait 10 s, then terminate and kill the runner process. The service keeps reporting
  `STOP_PENDING` with an advancing checkpoint meanwhile.
* Secrets: machine credential in DPAPI (`CRYPTPROTECT_LOCAL_MACHINE`, per-name entropy) with a Credential Manager fallback; never plain text.
  The `ProgramData\ComputeCoin` tree is restricted to SYSTEM and Administrators with `icacls`. Enrolment moves the credential out of `agent.toml`
  immediately; an old `~/.computecoin/agent.toml` is migrated (`service migrate`) and its bytes overwritten before deletion
  (best effort: SSD wear levelling, shadow copies and backups are not defeated; re-enrol to rotate when in doubt).
